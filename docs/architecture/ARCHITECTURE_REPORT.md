# Архитектурный отчёт проекта FallaF KR M Backend

## 1. ОБЩЕЕ ОПИСАНИЕ АРХИТЕКТУРЫ

Проект представляет собой REST API backend-приложение для управления финансовыми операциями инструкторов и разработчиков. Архитектура построена на основе **многослойной архитектуры (Layered Architecture)** с элементами **Dependency Injection (DI)** и **декларативного программирования**.

### Архитектурный стиль
- **Тип**: Многослойная архитектура (3-слойная)
- **Паттерн**: MVC (Model-View-Controller) с адаптацией для API
- **DI Container**: InversifyJS
- **Подход**: Декларативное программирование через декораторы

## 3. СТРУКТУРА КОМПОНЕНТОВ

### 3.1 Слои архитектуры

```
┌─────────────────────────────────────┐
│   Presentation Layer (Controllers)  │
│   - API Controllers                 │
│   - Public API Controllers          │
│   - Request/Response handling       │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│   Business Logic Layer              │
│   - Validation (io-ts)              │
│   - Business rules (в контроллерах) │
│   - External services (FreeKassa)   │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│   Data Access Layer                  │
│   - Prisma Client                    │
│   - Database queries                 │
│   - Session Store                    │
└──────────────────────────────────────┘
```

### 3.2 Компоненты системы

#### **A. Точка входа (main.ts)**
- Инициализация DI контейнера
- Настройка Express middleware
- Конфигурация сессий
- Статическая раздача фронтенда
- Обработка маршрутов

**Ответственность**:
- Bootstrap приложения
- Конфигурация HTTP сервера
- Интеграция Express + Inversify

#### **B. DI Container (container.ts)**
- Регистрация зависимостей
- Биндинг сервисов
- Автоматическая загрузка контроллеров через декораторы

**Зарегистрированные зависимости**:
- `PrismaClient` - Singleton
- `SessionStore` - Singleton (PrismaSessionStore)
- `FreeKassa` - Singleton
- `IsSignIn` - Middleware

#### **C. Контроллеры (Controller/)**

**1. API Controllers (защищённые)**
- `Controller_API_User` - Управление пользователями
- `Controller_API_Money` - Финансовые операции
- `Controller_API_FreeKassa` - Платежи (защищённые)

**2. Public API Controllers (публичные)**
- `Controller_PublicAPI_FreeKassa` - Webhook для FreeKassa

**Паттерн**: Controller Pattern с декораторами
- `@controller("/path")` - Регистрация маршрута
- `@httpGet/@httpPost/@httpPut/@httpDelete` - HTTP методы
- `@inject("Service")` - Внедрение зависимостей
- `@request()/@response()` - Доступ к Express объектам

#### **D. Middleware (Middleware/)**
- `IsSignIn` - Проверка аутентификации

**Паттерн**: Middleware Pattern
- Наследование от `BaseMiddleware`
- Регистрация через строковый идентификатор
- Использование: `@httpGet("/path", "IsSignIn")`

#### **E. Библиотеки (lib/)**
- `FreeKassa` - Интеграция с платёжной системой
  - Генерация подписей
  - Создание URL для оплаты
  - Валидация платежей

#### **F. Валидация (io_ts/)**
- `UserRole` - Кастомный тип для валидации ролей

**Паттерн**: Runtime Type Validation
- Использование io-ts для валидации входных данных
- Комбинирование с fp-ts для обработки результатов

#### **G. База данных (prisma/)**
- `schema.prisma` - Схема БД
- `seed.ts` - Начальные данные

**Модели данных**:
- User, UserInvate, Session
- Instructor, InstructorHistory
- File, Dev, DevHistory

## 4. ПАТТЕРНЫ ПРОЕКТИРОВАНИЯ

### 4.1 Используемые паттерны

#### **Dependency Injection (DI)**
- **Реализация**: InversifyJS
- **Применение**: Все контроллеры, middleware, сервисы
- **Преимущества**:
  - Слабая связанность компонентов
  - Легкое тестирование (моки)
  - Централизованное управление зависимостями

#### **Decorator Pattern**
- **Применение**:
  - `@controller` - Регистрация контроллеров
  - `@httpGet/@httpPost` - Регистрация маршрутов
  - `@inject` - Внедрение зависимостей
- **Преимущества**:
  - Декларативный стиль
  - Меньше boilerplate кода
  - Автоматическая регистрация

#### **Middleware Pattern**
- **Применение**: Аутентификация, обработка запросов
- **Реализация**: Express middleware + Inversify BaseMiddleware

#### **Repository Pattern (частично)**
- **Текущее состояние**: Прямой доступ к Prisma из контроллеров
- **Рекомендация**: Выделить слой Repository для изоляции БД

#### **Service Layer Pattern (отсутствует)**
- **Текущее состояние**: Бизнес-логика в контроллерах
- **Рекомендация**: Выделить слой Service для бизнес-логики

#### **Factory Pattern**
- **Применение**: Создание URL для FreeKassa

#### **Strategy Pattern (частично)**
- **Применение**: Различные стратегии валидации через io-ts

### 4.2 Функциональное программирование

#### **Использование fp-ts**
- `pipe` - Композиция функций
- `Either` - Обработка ошибок (Left/Right)
- `isLeft/isRight` - Проверка результата валидации

**Пример**:
```typescript
const data = io_ts.type({...}).decode(req.body)
if(isLeft(data)) return res.status(400).json(data.left)
// Использование data.right
```

## 6. БЕЗОПАСНОСТЬ

### 6.1 Аутентификация
- **Механизм**: Session-based authentication
- **Хранение**: База данных (PrismaSessionStore)
- **Валидация**: Middleware `IsSignIn`
- **Пароли**: Хеширование через `password-hash`

### 6.2 Авторизация
- **Модель**: Role-Based Access Control (RBAC)
- **Роли**: Admin, Manager, Instructor, User
- **Проверка**: В контроллерах через `req.session.user_role`

### 6.3 Валидация данных
- **Runtime валидация**: io-ts
- **Типизация**: TypeScript (compile-time)
- **Входные данные**: Все POST/PUT запросы валидируются

### 6.4 Проблемы безопасности

⚠️ **КРИТИЧЕСКИЕ**:
1. **Финансовые endpoints без авторизации**:
   - `/api/money/instructors` - GET (публичный)
   - `/api/money/instructor` - PUT (создание без авторизации)
   - `/api/money/instructor/:id/addMoney` - PUT (пополнение без авторизации)
   - `/api/money/files` - GET (публичный, но фильтруется по роли)

2. **FreeKassa webhook не обрабатывает платежи**:
   - Только логирование данных
   - Нет проверки подписи
   - Нет обновления балансов

3. **Hardcoded значения**:
   - В `Controller_API_FreeKassa.getPayUrl()` захардкожены order_id, inst_id, amount

## 7. АРХИТЕКТУРНЫЕ РЕКОМЕНДАЦИИ

### 7.1 Выделение слоя Service

**Проблема**: Бизнес-логика смешана с контроллерами

**Решение**:
```
Controller → Service → Repository → Prisma
```

**Пример структуры**:
```
src/
  Service/
    UserService.ts
    MoneyService.ts
    PaymentService.ts
```

**Преимущества**:
- Разделение ответственности
- Переиспользование логики
- Упрощение тестирования

### 7.2 Выделение слоя Repository

**Проблема**: Прямой доступ к Prisma из контроллеров/сервисов

**Решение**:
```
src/
  Repository/
    UserRepository.ts
    InstructorRepository.ts
    FileRepository.ts
```

**Преимущества**:
- Абстракция от ORM
- Легкая замена Prisma на другой ORM
- Централизация запросов к БД

### 7.3 Улучшение обработки ошибок

**Текущее состояние**:
- Разрозненная обработка через `.catch()`
- Нет централизованного error handler

**Рекомендация**:
- Создать `ErrorHandler` middleware
- Использовать кастомные классы ошибок
- Единый формат ответов об ошибках

### 7.4 Добавление валидации на все endpoints

**Проблема**:
- Не все endpoints валидируют входные данные
- Нет валидации параметров URL

**Рекомендация**:
- Создать декоратор `@validate()`
- Использовать io-ts схемы для всех входных данных

### 7.5 Улучшение безопасности

**Критические задачи**:
1. Добавить авторизацию на все финансовые endpoints
2. Реализовать обработку FreeKassa webhook
3. Добавить проверку подписи в webhook

5. Добавить rate limiting
6. Добавить CORS настройки

### 7.6 Логирование

**Текущее состояние**:
- Минимальное логирование (только console.log)

**Рекомендация**:
- Внедрить структурированное логирование (Winston, Pino)
- Логировать все важные операции
- Разные уровни логирования (dev/prod)

### 7.7 Конфигурация

**Текущее состояние**:
- Переменные окружения через `process.env`
- Нет валидации конфигурации

**Рекомендация**:
- Создать `Config` класс с валидацией
- Использовать io-ts для валидации конфигурации

### 7.8 Тестирование

**Текущее состояние**:

**Рекомендация**:
